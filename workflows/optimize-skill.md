# Workflow: optimize the Skill package

1. Treat user feedback and archived prompt evidence as evidence about a decision, not automatically as a new fixed prompt rule.
2. Classify the issue as engine, router, recipe, chassis selection/translation, theme compiler, composition planner, prompt renderer, carrier mechanics, backend, review, or case-specific execution.
3. Distinguish **source inventory** from **family grammar**. A successful case can prove that a soft-image / crisp-printed chassis, title rhythm or density logic is real; it cannot make its purple, flower, exact frame geometry, words or symbols universal.
4. Treat repeated color across unrelated recent outputs as a cross-theme failure, not as evidence that the family needs one signature accent. Require a fresh palette record and pixel-level palette audit for each theme.
5. Check whether the failure appears across multiple themes or only one case.
5. If cross-theme, update the smallest reusable rule in design DNA, router, chassis, compiler, planner, renderer, workflow, diagnostic and quality gate together.
6. If case-specific, update only `cases/<case>/`; do not turn a case repair into a default.
7. When a change removes generic furniture, verify energy substitution: the resolved theme/carrier/chassis system must retain authored pressure rather than leave a polite isolated subject.
8. When a change adds graphic pressure, verify it is not copied source furniture, fake data, HUD costume or a subject-destroying scaffold.
9. Ensure mode, chassis intensity and production route can change independently without rewriting the fixed visual DNA.
10. Validate metadata, links, directory layout, schemas, version synchronization, stale references and JSON syntax.
11. Record the change in memory only as a concise project note.
12. Report package changes and validation; generate a test image only when the user requests it or when the optimization protocol explicitly calls for a test.
